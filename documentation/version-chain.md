# Version chain

Every client build Seihai can present as is one **step** in an ordered chain, oldest first. A step is a name (label, token, link date, basis) plus a small **delta**: only what that build changed against the build before it. The first step starts from `ORIGIN`, a fully written-out 1.33 row. Resolving the chain gives the 26 rows of `PROFILES`, so the rest of the client still reads one `VersionProfile` per version and nothing downstream changed.

Code: `client/src/protocol/chain.rs`. `profile.rs` keeps the row types and the shared rule constants (`DEATH_205`, `COMBAT_205`, the tamper-check constants); `PROFILES` there is the resolved chain.

## What a step holds

```rust
Step {
    version: ClientVersion::V217,
    label: "2.17",
    token: "GNW22122",
    date: "",
    basis: Basis::Binary,
    delta: Delta {
        plo: IdDelta { plus: &[179], plus_ranges: &[(175, 177), (181, 185)], ..IdDelta::NONE },
        pli: IdDelta::plus(&[39, 40, 43, 44, 45]),
        tampercheck: Some(true),
        tamper: Some(Some(TAMPER_217)),
        npc_max: Some(73),
        heights: Some(true),
        ..Delta::NONE
    },
    source: "binary (2.17.1): TAMPERCHECK (39) with its constant, ...",
    unknown: &[Unknown { area: "props", what: "other-player prop parser was not read; ..." }],
}
```

- `delta`: `None` means "as the step before", `Some(x)` sets the value (`Some(None)` sets an optional field to nothing). The four id sets (server ids handled, client ids sent, own-player props, other-player props) use `IdDelta`: ids and inclusive ranges to take out, then to put in.
- `source`: where the delta comes from (a binary, the shipped release notes, server source, a lab capture). One line.
- `unknown`: what the notes do **not** settle for this build. A value that is not known stays the previous step's value and the step says so here; nothing is filled in. Every step with no binary behind it (`Basis::Inferred`) must have at least one entry, and so must a step whose delta is empty.

The resolver is a `const fn`, so `PROFILES` is built at compile time and keeps its type, `&'static [VersionProfile]`.

## The handler-change table

`seihai --version-chain` prints, for each step, what changed against the step before: server ids the client gains or loses a handler for, client ids it can send, prop ids its parsers accept, framing and login, files, levels, death and combat rules, UI switches. Then the step's `unknown` entries and `source`. Ids carry their gs2lib names.

```
seihai --version-chain                          # text, all steps
seihai --version-chain --version 2.17           # one step
seihai --version-chain --chain-format tsv       # step, label, token, basis, kind, area, field, detail
seihai --version-chain --chain-format md        # the table at the bottom of this page
```

The table is **generated by comparing the resolved rows**, never written by hand, so it cannot disagree with the profiles. Two copies are checked in and a unit test fails if either is stale:

- `documentation/version-chain.tsv`: `seihai --version-chain --chain-format tsv > documentation/version-chain.tsv`
- the block between the markers at the bottom of this page: paste the output of `--chain-format md` there.

## Adding a version

1. Add a value to `ClientVersion` and to `ClientVersion::all_versions()` (`protocol/version.rs`), at the place the build belongs in the order (the chain follows that order).
2. Add a `Step` to `CHAIN` in `chain.rs`, right after the build it follows. Give the label, token, date and basis, then only the fields that build changed. Put in `source` how you know, and in `unknown` what you do not.
3. Run `cargo test -p seihai-core --lib protocol::`. The tests tell you what is missing:
   - `deltas_are_minimal`: an id you add was already there, or an id you remove was not.
   - `deltas_are_effective_and_empty_steps_explain_themselves`: a field you set to the value it already had, or an empty delta with no `unknown`.
   - `inferred_steps_say_what_is_unknown`.
   - `rows_match_version_profile_toml`: if Graal_analysis has a TOML entry for the build, regenerate `profile_toml.tsv` (see `version-profiles.md`).
4. Regenerate the two checked-in tables (commands above).

No logic changes: the dispatcher, the login code and the gates all read the resolved row.

If the new build lands between two existing ones, the step after it must be re-checked: its delta was written against the old neighbour, and `deltas_are_minimal` will flag ids that are now already present.

## Tests that keep behaviour unchanged

`protocol/profiles_golden.txt` holds the `Debug` form of each of the 26 rows as they were written by hand before the chain existed. `chain_equals_the_hand_written_rows` checks every one of them byte for byte against the chain. Builds added later need no line in that file.

## What the chain does not decide

- It does not say a value is true; it says what Seihai's row holds and how well it is backed. Rows marked inferred are the builds with no binary (2.1 to 2.16, 2.3).
- The table lists changes in Seihai's profile fields only. Behaviour of a build that is not a profile field (payload layouts, timings) lives in `protocol.md` and the notes.
- Found while building it (left as it was, so behaviour is unchanged): the 1.41 row carries the 2.05 death and combat rules, because it was built from the 2.05 template; 1.42 clears them. No 1.41 handler was traced. The TOML lists GLEVNW01 (`.nw`) as readable by 1.41 and 1.42, while the rows of 1.33 to 2.04 have `.graal` only.
