# 2.05 kicked on public servers (2026-10-31)

## What was seen

The user ran main (`5a67e9d`) from their own machine:

- 2.05 on Sharp3D TEST: `Disconnected for sending invalid packets.`
- 2.05 on GServer-RS: the connection closed with no message.
- 2.17 on Sharp3D TEST ended with no message. 2.17 on Testbed played.

`packets.log` from the Sharp3D 2.05 run has six server frames in all: `FLAGSET`,
`FILESENDFAILED` (empty name), `FILESENDFAILED` (13 characters), `FLAGSET`,
`FILESENDFAILED` (2 characters), then the disconnect. No login burst came first
(no signature, props or board). The server was answering Seihai's messages
before it had finished the login, and GServer-v2 kicks after more than 5 unknown
ids or unknown props. The log held received frames only, so the messages Seihai
sent are not known.

2.05 had no working public session before this. On 2026-10-30, GServer-RS closed
a 2.05 login and a gs2 server refused it by version
(`public-gserver-2026-10-30.md`). Today's walk and flag changes (#291, #294) do
not reach 2.05. A lab capture confirms that 2.05 still walks with X/Y and sends
every flag.

## What changed for 2.05 since that run

The focus pause (`0581d50`, 2026-10-30) sends STATUS whenever the paused bit
changes, followed by X/Y/SPRITE. A window that opens without the focus sent both
in the first frames after the login line, before the server's first byte. STATUS
went out as paused, on a zero base, and the position was the offline default.
In a lab capture with the account check held 3 s:

    C>S f0 +0ms   LOGIN
    C>S f1 +1ms   LANGUAGE
    C>S f2 +28ms  PLAYERPROPS STATUS=1
    C>S f3 +28ms  PLAYERPROPS X=30 Y=30 SPRITE=2
    S>C f0 +1002ms ...

The real 2.05 sends nothing between its login frame and the server's burst. Both
lab GServers (patched beta4 and stock efb5b90) accept these early messages, so
the lab never flagged them. 1.41, which is also gen 3, did the same.

Whether these early messages caused the Sharp3D kick is not proven. That needs
the server's own log, or a run with the new send log.

## Fixes

- **Nothing before the level.** The hidden and paused bits go out only once the
  level has arrived (`seihai-mae` main loop). Lab, same 3 s hold: 2.05, 2.22,
  1.39 and 1.41 send only the login line (and the language) before the
  server's first frame.
- **One line per message.** `net::check_wire_message` requires an id byte of
  0x20 or more, one closing `\n` and no `\n` inside. The servers split a frame
  at each `\n`, and on gen 3 every message carries its own iterator step. A
  message that breaks this rule would put the server one step off for the rest
  of the session, and every later message would then read as garbage.
  `send_messages` and the bundled login frame drop such a message, do not step
  the iterator for it, and log it (`not sent: malformed message ...`).
- **Sent messages in `packets.log`.** With `debug=1`, each sent message is
  written before its cipher: `send id N len L <bytes>`. A dropped one is
  written as `send DROPPED (<reason>) ...`. The login line is not written,
  because it holds the password. Received frames now show their first bytes
  too: `recv frame len L: id N ...`.

## Still open

- **2.17's bundled login.** Seihai sends the login line, `LANGUAGE` and the
  tamper check in one frame, as the real 2.17.1 does. Stock GServer-v2 beta4
  drops everything after the login line in that frame, so its gen-3 iterator
  falls one step behind. Only the lab patch (`gserver-beta4-lab.patch`, fix 1)
  keeps that frame working. A real 2.17.1 would fail the same way on a stock
  beta4.
- **5.07 to 6.037** were not run here. The lab beta4 sets the generation for
  the whole server, and the 2.x server does not allow them. The STATUS gate and
  the line check are the same code for every build.
- **The server crashes** (Sharp3D, hastur) are not explained by anything on the
  client side. hastur turned the 2.17 login away by version.
